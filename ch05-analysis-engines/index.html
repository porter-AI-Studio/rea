第 5 章 · Part 2：安裝與上手

接上分析引擎：Hopper、Ghidra 與 JDK

先確認分析目標，再讓 REA 接上適合的本機引擎。

REA 與引擎各做什麼

前章完成 CLI 與 Agent 的註冊後，下一步是確認目標需要哪一種分析。REA 提供一致的 CLI 與 MCP 介面，負責選擇 provider、呼叫工具並回傳附帶來源與限制的 Evidence；原生程式的反組譯與反編譯仍由本機已有的 Hopper、Ghidra 或 IDA 完成。要讀取已抽出的 JavaScript 目錄或 Electron ASAR，則可直接使用靜態應用分析，不必為此安裝原生反編譯器。這個分流也決定排障方向：JavaScript 調查失敗，先看目標檔案與應用圖；原生調查失敗，才檢查 provider、JDK 與主機支援範圍。

三種原生引擎各自建立自己的分析結果，彼此不等價。Ghidra provider 文件說明，選定 provider 後會綁定該目標；執行時錯誤不會自動改用另一個引擎。不同引擎產生的偽程式碼，不能單靠文字相同與否判斷語義。選擇時要看作業系統、目標格式、已安裝的工具，以及本次需要的操作。

先列出可用的 provider

rea providers 回報目前可用的深度分析引擎；rea capabilities 可看相關能力。兩者是判斷環境狀態的起點，不能把「列出某 provider」誤當作目標檔案一定受支援。REA 會在只有一個候選引擎支援目標時自動選取；若多個候選者同時支援，應明確指定，避免模糊選擇。以下兩行直接摘自官方 CLI 文件。

列出引擎與能力
rea providers --json
rea capabilities --json

Hopper 是獨立軟體，授權與示範模式限制由廠商決定。官方安裝流程中，rea setup 可在列出變更並取得核准後代為安裝 Hopper；Ghidra 與 IDA 則使用操作者既有的安裝。REA 可在需要時啟動 Hopper，無須先手動開啟；但應用程式視窗或系統對話框仍可能出現，REA 不會替使用者回答。IDA 有自己的 adapter 與接入模式，已開啟的 GUI 目標和 headless 目標做法不同；若工作以 IDA 為主，先核對IDA provider 文件和已安裝套件的功能邊界。

Ghidra 與完整 JDK

Ghidra 需由操作者自行安裝，REA 不會代為下載、安裝或升級 Ghidra 與 Java。以素材記錄的 Ghidra 12.1.x 流程為例，先確認安裝目錄有 support/analyzeHeadless；Windows 對應 support/analyzeHeadless.bat。Java 必須是符合該份 Ghidra 安裝檔宣告範圍的 64 位元完整 JDK，包含 javac，不能以精簡 JRE 代替。環境變數 GHIDRA_INSTALL_DIR 指向 Ghidra 安裝根目錄；JAVA_HOME 指向完整 JDK；若 java 與 javac 已在 PATH 中，可省略不設。下例逐字取自本章素材，路徑只是範例，應換成自己的實際安裝位置。

Ghidra 路徑與診斷範例
export GHIDRA_INSTALL_DIR=/opt/ghidra_12.1.4_PUBLIC
export JAVA_HOME=/opt/jdk-21   # 若 java/javac 已在 PATH 中，可省略
rea doctor --json

若只想診斷 Ghidra，就限定 doctor 的檢查範圍；不帶範圍的健康檢查可能因其他未安裝的整合項目而顯示整體未就緒，不能直接推論 Ghidra 壞了。診斷會檢查版本、headless 啟動器、完整 JDK 及主機條件。通過後，再用 rea providers --json 看 Ghidra 是否成為可選引擎。流程是安裝、指定路徑、診斷、選取 provider；rea setup 是將 REA 註冊至 Agent 的另一步。

只檢查 Ghidra
rea doctor --provider ghidra --json
⚠️
版本說法有差異

截至 2026-10-13，本章素材中的舊版教學舉 Ghidra 12.1.2，新版文件寫 12.1.x 並以 12.1.4 驗證；JDK 條件應以實際 Ghidra 安裝的宣告為準。REA 更新頻繁，安裝前請核對 官方安裝文件及目前 npm 套件邊界，不要將這些範例版本視為永遠有效。

明確選擇引擎，讀取原生目標

官方 CLI 文件提供下列原生命令。把 /absolute/path/to/program 換成你有權分析的實際檔案；main 與 0x1000 是文件中的函式選擇範例，不能假設任何目標都有這個名稱或位址。analyze 提供概觀，search 查找文字，function 取得函式資料，decompile 回傳偽程式碼。回傳內容是分析引擎對編譯產物的觀察，不是原始碼。

官方原生調查命令
rea analyze /absolute/path/to/program --provider ghidra --json
rea search /absolute/path/to/program "search" --provider ghidra --json
rea function /absolute/path/to/program main --provider ghidra --json
rea decompile /absolute/path/to/program 0x1000 --provider ghidra --json

Ghidra 第一次匯入會建立暫時資料庫，完成預設自動分析後才開放查詢；這段冷啟動時間可能讓大型目標的首次回應比後續查詢慢。若 Agent 客戶端先逾時，應查看工作是否仍在進行及文件中的會話恢復方式，不要把客戶端等待逾時直接寫成「分析失敗」。在 Windows 上，官方 P0 文件把 Ghidra 視為實驗性、唯讀、且僅接納其列明的本機 NTFS 原生 PE 範圍；其他主機與格式不能從 Linux/macOS 流程直接類推。

ℹ️
保留證據與未知

搜尋不到字串，不代表檔案裡絕對沒有文字；Ghidra 的字串清單只涵蓋它定義為字串的 Data。函式偽程式碼、呼叫邊及其未解析目標也各有範圍。記錄 provider、目標與 Evidence 限制，下一章才有基礎向 Agent 提出可查證的問題。

實際操作時，可把診斷回報當作待辦清單逐項處理。例如缺少 headless 啟動器與缺少完整 JDK，是不同的安裝問題；provider 已可用但目標格式不在接受範圍內，則應回到目標和主機邊界查證。若同一台機器同時裝有多種引擎，在命令中明寫 --provider ghidra 也有助於日後重現同一份調查。Ghidra 的暫時匯入會保留來源檔案的身分，但分析結果依然可能受到自動分析、符號與目標位元組影響；換一個版本的執行檔，應視為新目標重新核對。

選擇引擎之前，也要先確定檔案是否為原生目標：副檔名只能提供提示，真正可用的操作仍由目標內容與 provider 的接受範圍決定。把診斷輸出與目標格式一起保存，能避免往後把環境問題誤判為分析結論。

同一份二進位檔若交給兩個 provider，應分別保存各自的 Evidence，再比較共同可核對的位址、位元組與符號線索。偽程式碼中的變數名稱與排版是分析器的呈現方式，不應當作原作者命名的證據。遇到未解析的間接呼叫或缺少字串，也要記錄是哪個引擎、哪一次匯入產生的結果，方便日後換方法複查。

下一章將從一個明確功能出發，示範如何用一句話要求 Agent 找線索、標示證據，並留下尚未解決的問題。
