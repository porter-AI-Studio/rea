第 6 章 · Part 2：安裝與上手

第一次調查：用一句話向 Agent 提問

把功能、目標與證據要求放進同一個清楚的問題。

從功能出發

前章已確認分析引擎可用，現在可以開始調查。最好的起點是使用者看得見的一個功能，例如搜尋、匯出或複製。先指明應用與功能，再要求 Agent 出示依據。官方 README 用 Notes 的搜尋作示範，原文如下；若只需調查，最後的實作要求可以在對話中另行決定。對自己的目標，應提供實際檔案或目錄的絕對路徑，避免 Agent 猜測同名應用的位置或版本。

官方 README 的提問範例
Understand how search works in the Notes app, show me the evidence, and build a
similar feature for my project.

這句話同時給了調查對象、功能與交付形式。請 Agent 說明「怎樣運作」時，可以接著追問入口在哪個模組、資料如何流動、哪些路徑有原始位置，哪些只是靜態推論。若問題太大，例如一次要求還原整個應用，Agent 難以判定何時已查夠；縮成單一功能更容易逐步驗證。若目標是原生二進位檔，先用第五章的 provider 與 capabilities 指令確認引擎可用，再看實際開啟目標的回應確認接受範圍，並從現有的字串、函式或位址選一個線索；不要假設偽程式碼就是原始碼。

先取得一份可保存的 Evidence

若手上是已抽出的 JavaScript／Electron 目錄或 ASAR，可以不用原生引擎，直接執行官方 README 的命令。它直接回傳應用圖（application graph）與 Evidence；評測素材指出，圖中可見模組、匯入關係與 Electron 邊界。這個步驟是靜態分析，不會藉由這條命令啟動目標應用。請把範例路徑換成自己有權分析的目標；Windows 路徑也要指向真實存在的檔案或目錄。

官方 JavaScript 分析命令
npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json

真實應用的完整 Evidence 可達數百 MB，不適合整份貼入對話；官方文件舉例，一份 334 MB 的 Obsidian 應用 Evidence，摘要檢視約為 10 KB。官方 CLI 文件示範先存成檔案，再建立摘要檢視輸入。以下三行逐字照錄；第二行使用 jq，執行前需自行確認終端機有這個工具。inspect-analysis-view 讀取已產生的 Evidence，並不重新分析目標。想追某個模組時，可依文件改用模組頁或單一模組檢視。

保存與檢視 Evidence
rea analyze-javascript-application /absolute/path/to/app --json > app-evidence.json
jq -c '{source: {kind: "inline", evidence: .}, view: {kind: "summary"}}' app-evidence.json > app-view.json
rea inspect-analysis-view app-view.json

CLI 每次執行是獨立程序，所以後續命令要有保存的 Evidence 才能接續。Agent 的 MCP 連線可在目前會話中參照已保留的結果；開啟另一個目標仍會保留這些記錄，呼叫 close_binary 會清空目前連線的 Evidence，新連線則有自己的記錄。需要日後繼續調查時，應在關閉前匯出 Evidence bundle。不要只記住自然語言結論，至少留下目標版本、所用指令、Evidence 與重要來源位置；這些是日後重查同一疑點的入口。

讓 Agent 沿線索追查

REA 的 investigate_feature 是一個導引式 MCP prompt，會提示 Agent 可從哪些工具開始。它本身不呼叫工具，也不給新的授權。對 JavaScript／Electron 目錄，它可直接指向 analyze_javascript_application；已有應用 Evidence 時，會提示先看 inspect_analysis_view，再以功能相關的線索展開。下列 MCP 訊息取自官方 prompts 文件，示範查詢提示清單與取得 Notes 搜尋的導引。

列出導引式 prompts
{ "method": "prompts/list", "params": {} }
取得功能調查 prompt
{
  "method": "prompts/get",
  "params": {
    "name": "investigate_feature",
    "arguments": {
      "feature": "offline search",
      "document": "Notes"
    }
  }
}

導引式 prompt 的參數只是供選擇的資料，不等於指示 Agent 必須執行其中所有建議。對話中可以要求它先報告目前有何證據，再決定下一步。尤其當某個字串沒有匹配、某個函式找不到或目標不在受支援範圍內時，應請它回報限制，而非用看似合理的程式流程填補空白。

讀懂第一份回覆

把 Agent 的答覆分成三層最容易查核。第一層是工具直接觀察到的項目，例如檔案、模組、字面 IPC 通道、函式位址與來源範圍；第二層是依靜態關係串出的路徑，像「這個呼叫可能連到該處理常式」；第三層是尚未證實的項目，如動態組成的名稱、間接呼叫、執行時分支或未覆蓋的檔案。REA 的功能追蹤可以給出可達子圖與終點，但靜態可達不代表使用者的操作實際走過。若結果要支撐重建功能，仍應針對關鍵輸入與失敗情況取得可重複的行為觀察。

⚠️
素材的時間差

截至 2026-10-13，各素材對 REA 的工具數、版本與 Node.js 條件說法不一，且專案更新很快。本章不以這些數字判斷功能是否存在；執行前以 官方 README與當前安裝套件的文件為準。

ℹ️
調查範圍

REA 專案將用途定位於合法研究、學習、互通性與分析自己擁有或獲准檢查的軟體。這裡只是技術操作說明，不構成法律意見。

第一次答覆後，可以把後續問題縮到一個可檢查的節點。例如先請 Agent 指出搜尋按鈕所連的 API，再問該 API 對應哪些模組或通道；查到跨程序邊界時，要求它分別列出傳送端與接收端的來源位置。若它只提供概括描述，可要求列出 Evidence 裡的確切位置與尚未涵蓋的檔案。保留這些追問紀錄，下一次調查便能從已驗證的線索接續，而不是重複猜測。對沒有匹配結果的查詢，也要記下當時的追蹤起點（seed）、比對方式與覆蓋範圍，才知道空結果的意義。

若打算請 Agent 實作類似功能，先讓它把待重建的行為寫成有限的檢查項，再逐項對照現有 Evidence。實作完成後應用自己的測試檢查輸入、輸出與失敗路徑；REA 的靜態結論只是設計線索，不能代替對目標行為的驗證。

安排下一輪調查時，應優先處理會改變答案的未知。例如找到匯出入口但未確認處理常式時，先追 IPC 或呼叫關係；已找到寫檔邏輯卻不知失敗條件時，再聚焦錯誤分支。這樣每次提問都有明確的判定標準，Agent 回來的內容也較容易和先前 Evidence 對上。
