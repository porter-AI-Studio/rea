第 7 章 · Part 3：分析目標

JavaScript 與 Electron 應用

沿著模組與 IPC 邊界，查出一個功能跨程序的路徑。

先辨認手上的產物

上一章用一個功能提問建立調查範圍。JavaScript 與 Electron 特別適合練習這件事：安裝產物常保留可解析的模組、字串與封裝結構，REA 可以從抽出的應用目錄或 ASAR 建立靜態應用圖，不需先接 Hopper、Ghidra 或 IDA。官方 CLI 文件說明，通用 rea analyze PATH 在未指定提供者或快照時，會把目錄與 .asar 交給 JavaScript 工作流。這是讀取指定產物，不代表已觀察到應用實際執行。

應用圖整理入口點、模組、匯入關係、路由、source map、Electron 程序邊界、IPC 與原生外掛連結。source map 可能提供來源檔案與打包程式碼的對應線索，但映射存在不代表原始碼完整或與執行中的版本相同。若套件被壓縮、混淆，或以動態名稱組裝通道，靜態分析仍可能留下未知項；應查看結果列出的覆蓋範圍與限制，而非把缺席當作功能不存在。

ℹ️
分析目標的身分

在同一應用的不同版本間，比較時要保留目標位元組與 Evidence 的身分。官方工作流文件要求以已驗證的應用圖追蹤功能；原生外掛的交接也須對上精確的檔案摘要，才會連到既有原生 Evidence。

用官方範例建立應用圖

REA 的 JavaScript 與 Electron 指南提供一個小型 Notes 範例。下載並解壓該指南的範例 ZIP 後，文件用下列命令分析 notes-example 目錄；只需 Node.js 與 npm，不必安裝 Electron。執行時將範例絕對路徑換成你的解壓位置。結果可從 normalized_result.summary.ipc 看通道摘要，並從 normalized_result.graph 找來源位置。若對真實應用執行，完整 Evidence 可能很大，應照第六章的方法存檔並投影摘要。

官方 Notes 範例分析
npx -y rea-agents@latest analyze-javascript-application \
  /absolute/path/to/notes-example --json

這個範例有一個「Export notes」動作：使用者在頁面觸發匯出，renderer 呼叫公開 API，preload 透過 IPC 傳至 main，main 呼叫 CSV 格式化邏輯並寫入下載目錄。REA 能把字面通道與對應處理常式配對，讓 Agent 從頁面入口一路查到寫檔位置。這種配對建立的是程式碼中的關係；是否在某次按鈕操作中成功寫檔，仍是需要另外觀察的執行期事實。

追蹤 IPC 的兩端

以下程式碼逐字取自官方指南。preload 將 notes.exportCsv 暴露給頁面，並以字面通道 notes:export 發出呼叫。Agent 若只找到頁面的 window.notes.exportCsv()，還不能知道寫檔發生在哪裡；需要沿通道找 main 的處理常式。這也是 Electron 調查最常見的跨層邊界：畫面上的操作與有檔案系統權限的程序被分開放置。

官方範例：preload.js
contextBridge.exposeInMainWorld("notes", {
  exportCsv: () => ipcRenderer.invoke("notes:export"),
});

主程序的 handler 使用同一個通道名稱，組出下載目錄中的 notes.csv 路徑，呼叫 CSV 格式化函式，再將路徑回傳給頁面。這段程式碼足以回答「檔案在何處產生」的靜態問題；若要回答失敗時會怎樣，還需要檢查 writeFileSync 的錯誤路徑及呼叫方如何處理。不要從一條成功路徑猜測所有邊界情況。

官方範例：main.js
ipcMain.handle("notes:export", () => {
  const destination = path.join(app.getPath("downloads"), "notes.csv");
  writeFileSync(destination, toCsv(notes), "utf8");
  return destination;
});

在真實應用裡，可以以字面 API、字串或 IPC 通道為追蹤起點（seed）使用 trace_application_feature。它從既有應用圖回傳匹配線索、可達子圖與終點；遇到原生外掛時，只在摘要精確相符的情況下連接既有 Hopper 或 Ghidra Evidence，否則保留需要提供者（provider）分析的狀態。這種工作流不會暗中啟動原生提供者，也不會執行 JavaScript。若通道名稱是計算結果，或有多個可能 handler，結果應明列不確定性。

執行期觀察是另一份證據

靜態關係可以指引下一步，但不會證明使用者當下走過哪條路。REA 的 Electron observation 文件提供另一種模式：連到已存在的本機 Electron／Chromium CDP 端點，列出符合條件的頁面，再依目標 ID 觀察頁面、框架與資源。以下命令是文件原文；TARGET_ID 要換成前一行列出的真實 ID，端點也必須由操作者提供。這是對既有頁面的被動觀察，與主動點擊、啟動應用的情境擷取有不同邊界。

官方被動 Electron 觀察
rea list-electron-targets http://127.0.0.1:9223 --json
rea inspect-electron-page http://127.0.0.1:9223 TARGET_ID \
  --observation-ms 100 --json

這類觀察不會執行 renderer 程式碼、點擊、導航或呼叫 IPC，也不會關閉目標應用。它可以提供頁面與資源在某一時刻的執行期 Evidence；靜態圖推得的關係，若靜態應用圖與執行期 Evidence 都已取得，可透過 reconcile_javascript_runtime 工作流對照；結果仍須區分靜態推論與執行期觀察。兩份 Evidence 要標清來源與時間，避免把「程式碼裡可達」寫成「使用者操作已發生」。

⚠️
範例與版本界線

截至 2026-10-13，各來源對 REA 版本與功能數量說法不同，執行前以 官方 README及已安裝版本文件為準。Notes 是官方教學範例，不能把它的通道名稱、寫檔路徑或結果數量套用到其他 Electron 應用。

讀到 source map 時，先把映射位置當成尋找程式碼的導覽資訊，再回到打包產物與 Evidence 核對。

若同一個功能跨越 JavaScript 與原生外掛，應分別描述 JavaScript 端看見的匯出名稱、實際外掛檔案，以及原生引擎對該檔案的分析結果；中間缺少精確身分對應時，不要直接接成單一路徑。

要比較兩個應用版本，也應各自建立應用圖後再做版本比對：官方工作流對不完整覆蓋會留下 unknown，而不是把未見的模組一律判定移除。這些限制讓結論能回到實際產物核對。

若畫面中的名稱與打包程式碼中的名稱不同，可先從畫面文字、事件或網路端點找字面線索，再沿模組匯入與 API 邊界逐層縮小範圍。若找不到唯一對應，不要自行補出通道名稱；保留候選項與來源位置，必要時再用已存在的執行期頁面觀察查證。這樣即使 source map 缺失，調查仍能清楚指出已知與未知。
