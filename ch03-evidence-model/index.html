第 3 章 · Part 1：認識 REA

證據模型：每個結論都要附憑證

知道答案從哪裡來，也知道它尚未證明什麼。

一段解釋為什麼還不夠

第二章的社群爭論提醒我們：流暢的 Agent 回答不等於可靠的逆向結論。即使偽程式碼看起來合理，分析也可能只涵蓋某個版本、某個函式或一條執行路徑。REA 因此把調查輸出組成 Evidence 記錄，讓讀者能回頭核對分析對象、使用的能力、得到的原始或整理後結果，以及它的限制。證據模型的作用不是替 Agent 自動判真，而是讓「這句話根據什麼」成為可回答的問題。

官方工具設計文件要求結果內聯回傳目標與 provider 身分、來源位置、Evidence 參照、涵蓋範圍及相關信心與限制；observed、derived、inferred 關係要分開。這些詞各有分量：觀察是工具從目標讀到或捕捉到的材料，推導是依明確規則整理的關係，推論則需要讀者檢查前提。缺少涵蓋資訊應記為 unknown，不能因為結果欄位為空就宣稱「不存在」。

讀一份 Evidence 要看什麼

獨立測試列出一份 JavaScript 分析 Evidence 的欄位，可依判讀順序分組：對象與環境包括 subject、environment、authority；操作包括 provider、analysis_profile、predicate_type、operation、parameters；結果與出處包括 raw_result、normalized_result、confidence、limitations、locations、evidence_links，另有識別用的 evidence_id。這份欄位快照不是所有版本永遠不變的 schema；先確認分析的是哪個位元組內容與環境，再看誰做了什麼操作，最後才看結果與連結到其他紀錄的線索。

例如「找不到 IPC handler」只在完成對相關檔案與邊界的檢查後才有意義。如果分析範圍不完整，較精確的說法是「在已檢查範圍內未找到」。官方文件也強調，relationship_coverage 的 complete 僅表示 provider 觀察到的直接關係集合沒有已知讀取上限，不能擴張為所有可能的執行期呼叫邊界都已被證明。對大型 JavaScript 產物，完整 Evidence 可能很大；先看摘要 view，再循位置回到原始紀錄，通常比把整份 JSON 直接塞進 Agent 對話更容易查核。

讀取結論時也要留意「來源位置」指向什麼。它可能是檔案路徑、函式地址、擷取紀錄或工具所產生的中間物。地址若沒有對上同一份位元組內容，或檔案路徑其實屬於另一個版本，結論就失去可重複性。因此 Evidence 的 subject 與環境欄位不是裝飾；它們讓後續讀者知道該回到哪一個目標、哪一次操作，才能檢查同一件事。

下列範例逐字取自 官方 CLI 文件：先把分析輸出存為檔案，再建立摘要 view。檔案路徑是文件中的占位值，請按自己的工作目錄替換。

Evidence 與摘要 view
rea analyze-javascript-application /absolute/path/to/app --json > app-evidence.json
jq -c '{source: {kind: "inline", evidence: .}, view: {kind: "summary"}}' app-evidence.json > app-view.json
rea inspect-analysis-view app-view.json
ℹ️
查核時要保留原始脈絡

摘要方便找重點，但若要支持具體結論，仍需連回完整 Evidence 的來源位置、涵蓋範圍與限制。工具輸出中的 unknown、partial 或 unsupported，應原樣帶入報告。

讓結果能保存與比較

一次調查的價值不只在當下得到答案。官方 CLI 文件提供匯入、匯出與比較 Evidence 的指令，用於保存可重現材料，或對照兩份已取得的紀錄。使用這些命令前，先確認每個絕對路徑都位於已核准的根目錄；匯出也不會在未明確指定 --overwrite 時覆寫既有檔案。這些命令不會憑空補出原始檔案或保證兩個版本完全等價；比較結果仍受輸入 Evidence 的可比性限制。

官方 Evidence 匯入、匯出與比較範例
rea evidence-import /absolute/path/to/evidence/bundle.json
rea evidence-export /absolute/path/to/evidence/bundle.json /absolute/path/to/evidence/canonical.json
rea compare /absolute/path/to/evidence/left.json /absolute/path/to/evidence/right.json

若新版程式的搜尋結果不同，先比對目標雜湊、provider、參數與分析環境，再比較具體差異。否則一份由不同分析範圍或不同引擎產生的紀錄，可能只是觀察方式改變，而不是目標行為改變。

從線索到「重建完成」仍有距離

找出一個函式，與做出可替代的功能，是兩件事。官方重建義務文件把應重現的行為列為 obligation：靜態應用圖可以產生候選義務，卻不能單獨證明執行期行為。必要義務要結案，須由同一份 manifest 綁定一次供足：唯一的實作負責人、必要的 parser／schema／domain 型別、涵蓋全部必要案例的 fixture，以及權限與原觀察相當、結果也收進 Evidence 的通過驗證器。矛盾、重複定義或負責人、殘留未知、缺少相依項及不可用的權限，都會讓結案維持開放或失敗。

這套要求刻意保守。只有靜態來源，不能證明執行期或程序行為；一般單元測試通過，也不能自動證明封裝後程式的整體流程。即使先標記 blocked 或 out-of-scope，也只是如實記錄目前不能驗證的範圍。官方的 verify:readiness 是專案自身的符合性驗證程序，並非供使用者對任意目標呼叫的公開 REA 工具；不要把它當成「一鍵證明重建正確」。

若要建立重建義務清單，官方提供 MCP 工具 build_reconstruction_obligation_ledger，也可用 CLI 命令 rea build-reconstruction-obligation-ledger。此流程會依同一份 manifest binding 建立可檢查的義務清單；矛盾、重複定義或負責人、剩餘未知、缺少相依項及不可用的權限，都會讓結案維持開放或失敗。截斷、不穩定、權限不可用或彼此矛盾的證據若被標成等價，或矛盾證據／受影響的比較缺漏，readiness 也必須 fail-closed。fail、unknown、unsupported、truncated 與 skipped 都不能彙總成 pass；保留矛盾證據本身不會導致失敗，隱去它或把它當成等價才會阻止通過。

最容易犯的錯，是把「找到一條可能的路徑」寫成「完整還原功能」。若同一功能有錯誤分支、取消流程、資料遷移或背景程序，單一正常案例只覆蓋其中一角。官方重建義務的設計要求把這些必要案例明列，再用與原觀察可比較的驗證結果逐一結案。還沒取得的案例應留下 unknown；互相矛盾的觀察應一併保存，讓後續調查知道爭點在哪裡。

⚠️
版本與結構可能變動

截至 2026-10-13，素材中的 Evidence 欄位與版本文件並不完全一致；例如官方 6.2 遷移文件已描述 MCP 結果結構改動。讀取舊快照或撰寫整合時，以正在使用的發行版契約與實際回傳為準。
