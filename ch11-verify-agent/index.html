第 11 章 · Part 4：實戰、評測與比較

verify:agent：量化評估 Agent 的逆向能力

讀懂評測究竟驗證了什麼，再看分數。

從案例走向可重複的檢查

上一章的 DX-Ball、Notion 與 TH04 展示了調查如何展開，但個別案例不能直接替 Agent 的工具選擇、證據引用與限制說明打分。REA 原始碼庫提供 verify:agent：讓真實的本機 Codex CLI 面對固定夾具與提問，經 REA MCP 工具完成任務，再從事件紀錄計算結果。官方將真實模型試驗列為手動執行；Vitest 驗證的是確定性評分器邏輯。這是原始碼庫的 npm script，應在該庫執行，不是已安裝 rea 的一般子命令。官方 Agent 評測說明及測試指南都列出以下原文指令：

官方 verify:agent 指令
npm run verify:agent

此 script 先經 build:cached，再啟動評測腳本。場景依序執行，因此總耗時取決於所選場景、模型及主機環境。官方允許用 REA_AGENT_EVAL_SCENARIOS 選取逗號分隔的場景 ID，以 REA_CODEX_CLI 選執行檔，並用 REA_AGENT_EVAL_MODEL 指定帳號支援的模型；未知或重複的場景 ID 會報錯。REA_AGENT_EVAL_REPORT_PATH 可另存 JSON，REA_AGENT_EVAL_TRANSCRIPT_DIR 可保留每個場景的完整 JSONL，方便回看工具結果與最後答案。

隔離的 Agent 如何工作

官方流程在拋棄式 HOME 與 CODEX_HOME 裡，以公開的 rea setup 安裝打包 skill 與 MCP 註冊，再以 standalone Codex 逐一執行。它不複製使用者設定、規則、外掛或歷史；若有認證資料，只暫時複製所需檔案，結束後即刪除。Codex 使用唯讀沙箱，停用網頁搜尋與額外 agent。這些條件使結果較容易歸因於打包後的 REA 整合，同時界定了未涵蓋的日常使用環境。

原生目標的「缺少 provider」場景只預先核准 open_binary 與 close_binary，使 Agent 能走到真正的提供者邊界並回報無法取得的證據。官方特別指出，這不等於驗證實際的原生分析引擎。每個場景結束後，腳本解析 Codex JSONL 中的 REA 工具呼叫與 token 用量，再交給評分器；若要查爭議，仍應讀逐字稿，而非只看總數。

十個場景測哪一種判斷

截至 2026-10-13，官方 main 評測腳本列出十個場景。它們不是十種反編譯準確率測試，而是不同的目標、提問與預期工具路線。下表逐列列出十個場景 ID；工具名稱代表「期望首個工具」，不保證每個主機都能完成後續分析。

場景期望首個 REA 工具關鍵檢查
nativeopen_binary缺少 provider 時說明限制，並關閉已開會話
asaranalyze_javascript_application命中 profileapi、profile:read 與 preload／contextbridge 詞組
asar-zhanalyze_javascript_application以中文提問，使用同一 desktop rubric；必要詞組為 profileapi、profile:read
javascript-module-viewanalyze_javascript_application先分析，再兩次檢視模組 view
missing-target無，預期不呼叫 REA要求 app 名稱或 artifact 路徑
javascript-export-shapeanalyze_javascript_application分析兩版來源後比較 export shape
managedinspect_managed_artifact接著檢視 members，辨認公開型別與進入點
browserlist_browser_targets被動觀察，不導航、不執行頁面程式碼，回報權限或可用性限制
navigation-contextget_navigation_context沒有原生會話時如實說明
address-contextinspect_address_context查指定地址；沒有會話時如實說明

missing-target 特別值得注意：旁邊即使有夾具，使用者未指出目標時，Agent 也不能自行挑一個分析。此場景的 expectedFirstTool 為 null；它要零次 REA 呼叫，並以結構化答案請求目標。這是在測「何時先問清楚」，不能拿來當分析能力的分數。

分數如何讀，哪些不能推論

報告 schema version 4 的每個場景記錄首個工具是否正確、必要工具子序列、相同工具與參數的重複呼叫、輸入驗證失敗、token 用量、最後答案與事實評估。單一場景要通過，必須同時符合以下條件：

  • Codex 程序以 exitCode === 0 結束。
  • 若場景預期首個工具為 null，就不得呼叫 REA；其他場景須呼叫 REA 並選對首個工具。
  • repeatedCallCount 與 inputValidationFailureCount 都是 0。
  • 場景要求的工具呼叫子序列須符合順序，而且 inputTokens 大於 0。
  • missing-target 須通過 targetClarificationPassed；有事實 rubric 的場景須通過事實評估；其他場景須同時滿足答案啟發式與認知線索檢查。

任一場景不通過，腳本以非零狀態結束並列出失敗 ID。打包 desktop 與 parser 比較場景有封閉的已知答案 rubric。Agent 須交出嚴格 JSON manifest，列出要求的 claim ID、值、Evidence ID、Evidence authority 與 confidence；評分器會把 manifest 的值逐一對照夾具 oracle 與已認證成功的 REA 結果，只有 Evidence ID 並不足夠。漏列、重複、多列、矛盾、來源錯誤或無證據支持的主張都會失敗。這裡的 factualCorrectness: passed 只保證設定好的 configured_fixture_claims，不能推廣到任意軟體的事實正確性。

⚠️
啟發式分數與總數都有解讀限制

其餘沒有事實 rubric 的場景會落在 not_assessed，依工具流程與文字啟發式判斷。answerTermCoverageMet 檢查必要詞組，epistemicCuePresent 檢查如「unknown」或「unavailable」的語詞，finalCitesEvidence 只看答案是否出現 Evidence ID。這些檢查可放行編造的敘述，不能證明結論受到引用證據支持；javascript-module-view 的選取器與涵蓋範圍尤其要人工看逐字稿。

頂層報告另有 evaluationScope、factualCorrectness 摘要、installation、scenarios 與 totals。totals 中的 correctFirstTool 是符合首個工具預期的場景數，repeatedCallCount 則是重複呼叫總數；兩者不能相除後稱為「逆向準確率」。inputTokens 與 cachedInputTokens 提供用量線索，也不能單獨推斷分析品質。若比較不同次執行，至少先對齊所選場景、模型與報告 schema，並查明失敗是工具不可用、路由錯誤，還是答案不符夾具。單次通過也不保證下次真實模型會給出同一答案。

⚠️
舊文章的數字與欄位不可沿用

CSDN 文章描述的是舊版七場景及 contentCriteriaMet、completionQuality、authorityHonesty 等欄位；截至 2026-10-13 的官方 main 是十場景、schema version 4，使用 answerTermCoverageMet、answerHeuristicsMet、epistemicCuePresent 等名稱。文章的 7/7 與 token 範例不可當實測結果。版本持續變動，執行前以官方 README及當前原始碼為準。

別把 Agent 評測當成引擎驗證

verify:agent 只用真實 Codex CLI 試驗指定情境下的路由、流程與部分已知主張。其他 client 的 verify:*-client lane 重在 MCP 設定與呼叫整合，使用本機假模型；原生引擎與瀏覽器等真實工具能力也各有測試 lane。另有 verify:readiness 專門檢查來源自有夾具的重建流程，並非 Agent 分數。官方重建就緒度文件給出的原文命令如下：

官方重建就緒度命令（另一條驗證流程）
npm ci
npm run verify:readiness

讀報告時先確認場景、模型、版本及逐字稿，再分辨 factualCorrectness 是 passed 還是 not_assessed。本章依官方文件與原始碼說明機制，沒有實際執行 verify:agent，因此不提供虛構分數。下一章將比較 REA 與 GhidraMCP、ida-pro-mcp 的工作範圍，協助決定該用哪一種工具橋接。
