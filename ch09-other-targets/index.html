第 9 章 · Part 3：分析目標

.NET、APK、韌體與網站觀察

從封裝格式挑選入口，讓每個結論保留自己的證據範圍

目標格式先於工具選擇

上一章把原生執行檔帶到函式、指令與資料。遇到 .NET 組件、Android APK 或韌體時，先辨認封裝層與可直接讀取的內容；網站則要觀察已開啟的頁面。相同的「這個功能怎麼做」問題，在這些目標上會產生不同證據：有些是檔案中的宣告，有些只是某次執行看到的現象。

.NET：先讀組件與 CIL

REA 的受控程式碼檢查直接讀取 PE/CLI 檔案，不載入或執行組件。先用 inspect-managed-artifact 確認組件與中繼資料，再用 inspect-managed-members 查看型別、簽章、方法內容、呼叫及欄位存取。原文提供的兩個起手指令如下；路徑需指向自己持有的 DLL。

原文：.NET 組件檢查
rea inspect-managed-artifact /absolute/path/Assembly.dll --json
rea inspect-managed-members /absolute/path/Assembly.dll --json

方法 token 屬於特定建置，不能拿舊版的 token 直接指認新版方法。跨版本比較須回到簽章與觀察到的結構。若組件宣告 P/Invoke，能先列出它想呼叫的原生入口，再以另行取得的匯出或函式證據核對；名稱相符仍不等於已證實執行時呼叫，也不等於知道原生實作。NativeAOT 的普通 CIL 方法主體可能不存在，應將原生映像交給適合的原生分析路徑，並保留工具對型別回復範圍的限制。

ℹ️
中繼資料不是完整執行路徑

缺少已宣告的原生匯入，不足以排除動態解析、產生碼或其他輔助程式。對未選取的型別與方法，也不要把「沒有回傳」寫成「不存在」。

APK：區分套件、方法與裝置

靜態 APK 分析透過使用者提供的 headless JADX 與完整 JDK 讀取 Manifest、類別、反編譯方法及靜態參照。先盤點套件和權限，再搜尋類別、選取方法。遇到同名多載時，先看類別結果並指定索引；工具不會在模糊結果中默選第一個。反編譯出的 Java 或 smali 是衍生表示，來源中的完整文字不保證語意完整，也不是執行軌跡。

原文：APK 靜態調查
rea inspect-android-package /path/Example.apk
rea search-android-classes /path/Example.apk MainActivity
rea inspect-android-class /path/Example.apk example.MainActivity
rea inspect-android-method /path/Example.apk example.MainActivity onCreate
rea inspect-android-method /path/Example.apk example.MainActivity select --overload-index 1
rea trace-android-references /path/Example.apk example.MainActivity
rea trace-android-references /path/Example.apk example.MainActivity --method-name onCreate

若問題涉及「裝置上實際裝的是哪一組 APK」，ADB 路徑先列裝置與套件，再取得 base 與 split APK。裝置路徑不是主機上的檔案；只有拉取後才可把本機檔案交給靜態分析。ADB 也有啟動應用、安裝、推送檔案等會改變裝置狀態的操作，必須把這類動作與唯讀查詢分開記錄。Flutter APK 可先辨認 libapp.so、Dart snapshot hash 與 ABI，卻不能靠字串池推定完整類別和函式。

這裡還有兩種常見的空白：反編譯方法找不到來源內容，可能因它是原生或抽象方法；靜態參照沒列出某次執行的呼叫，也不代表執行時沒有呼叫。報告應分別寫明方法本體是否可得、參照是否為靜態，以及是否另做裝置上的動態觀察。對 split APK，只檢查 base 檔會讓資源或程式碼覆蓋率不足；取得整組檔案後仍需按每個分析工具的支援範圍解讀。

原文：Flutter 建置辨認
rea identify-flutter-build /targets/Example.apk
rea inspect-dart-aot /targets/Example.apk
rea inspect-dart-aot /targets/Example.apk --abi armeabi-v7a

Apple 的 IPA 或 macOS .app 又是另一種組合：盤點結果可以指出 bundle、framework、資源與可執行檔候選。路徑相鄰只能形成 JavaScript 與原生元件之間的候選連結；若要解釋 dylib 載入，需再追查 Mach-O 的載入指令與搜尋路徑。

韌體：先找區段，再核對解包產物

韌體檔常包著壓縮資料、檔案系統與多個執行檔。REA 以使用者自備的 Binwalk 辨認區段，用 Unblob 解包；輸出包含來源偏移、檔案路徑、雜湊及限制。先讀區段，再明確指定一個不存在的輸出目錄進行解包，最後挑選已核對的子檔案做原生分析。不要把簽章命中直接寫成有效分割區，也不要把解壓後子檔的位址說成原始韌體中的執行位址。

原文：韌體區段與解包
rea inspect-firmware-regions /path/to/firmware.bin
rea extract-firmware /path/to/firmware.bin /path/to/new-output
rea extract-firmware /path/to/firmware.bin /path/to/selected-output \
  --offset 64 --length 4096 --max-depth 3

解包的 complete 只表示引擎在設定的深度與規則內完成工作；未知或加密區塊、預設的跳過規則及格式覆蓋率仍會限制結論。若要解釋設備上的真實行為，僅有靜態解包還不夠。

對於解出的每個子檔，先核對路徑與雜湊，再確認它究竟是設定檔、腳本還是可執行映像。對壓縮內容，父檔偏移與子檔解壓後位元組之間不能直接劃等號；若報告需要指出原始檔中的確切位置，應只引用工具有回報來源範圍的區段。

網站：觀察當下，而非重建所有歷史

網站觀察使用已在執行、由使用者擁有的 Chrome 系瀏覽器。原文要求明確啟用觀察、指定本機 CDP 端點與允許的完整 origin，然後列出頁面並以回傳的目標 ID 檢查。這是被動觀察：可回報頁面結構、腳本與有限的網路資訊，不會自動點擊、導覽或執行頁面 JavaScript。連線前發生的活動也不能事後補成觀察記錄。

原文：CDP 頁面觀察
export REA_BROWSER_OBSERVE_ENABLED=true
export REA_BROWSER_CDP_ENDPOINTS_JSON='["http://127.0.0.1:9222"]'
export REA_BROWSER_ALLOWED_ORIGINS_JSON='["http://127.0.0.1:3000"]'

rea list-browser-targets http://127.0.0.1:9222 --approved --json
rea inspect-web-page http://127.0.0.1:9222 TARGET_ID --approved --json

若要比較某項行為，REA 的 process capture 可執行明確指定的指令，保存終端、結束狀態及選定檔案的觀察，再比較兩次 capture。但執行環境與未列出的副作用仍可能影響結果；這不是隔離環境。Frida 則能把使用者撰寫的腳本載入指定程序，腳本在目標程序的權限下執行，結果也必須標成該次動態觀察。
