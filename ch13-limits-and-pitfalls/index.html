第 13 章 · Part 5：邊界與風險

限制、坑與版本變動

把「工具回了什麼」與「工具尚未查明什麼」一起讀。

先辨認失敗發生在哪一層

上一章比較了三種 MCP 路線；選了 REA 以後，調查失敗仍可能發生在不同層。CLI 能啟動，不等於原生分析引擎已就緒；Agent 收到結果，也不等於它讀完了完整 Evidence；新版程式能執行，更不代表舊快照可直接載入。因此排查應按環境、執行、輸出與版本依序縮小範圍。這四層是整理文件後的工作方法，不是 REA 的官方狀態分類。

環境就緒並非全有或全無

REA 的 JavaScript 靜態分析可在沒有 Ghidra、Hopper 或 IDA 的環境下執行；原生偽程式碼則依賴另行安裝的引擎。實測文章中，rea doctor 回報整體未就緒，但 JavaScript 分析仍成功。排查時要看特定提供者及目標所需的條件，不能只看單一健康布林值。以下診斷指令逐字取自該實測與Windows Ghidra 文件。

讀取結構化環境診斷
rea doctor --json

Windows Ghidra 文件只描述實驗性的唯讀 P0 邊界，包括受支援的主機、檔案類型與操作範圍。它明言這不代表與其他平台功能對等：GUI 狀態、註記、其他架構格式及 Hopper 專用操作都不在該邊界內。若是受管理程式碼（PE/CLI 映像，如 .NET），文件指向不執行目標的獨立提供者。遇到「Ghidra 能打開，但 REA 拒絕」時，先核對目標是否落在該提供者接受的目標範圍。

長時間啟動與大量輸出

這一節對應圖 13-1 的執行與輸出兩層：先判斷工作是否仍在進行，再檢查結果是否因範圍過大而難以閱讀。

原生引擎初次匯入與自動分析可能很慢。某篇介紹文章聲稱大型二進位檔的 Ghidra 冷啟動可達數百秒，短的 MCP 客戶端逾時會先到；官方 Windows 文件也提醒冷匯入可超過客戶端較短的預設逾時。兩者都不能推成每台機器固定耗時。排查時要區分提供者仍在分析、客戶端已逾時，或分析本身失敗；不要因 Agent 沒回話便推論二進位檔沒有線索。

⚠️
時間與資源數字只屬特定來源

介紹文章稱標準 MCP 逾時預設為 60 秒，大型二進位檔的 Ghidra 冷啟動可達 330 秒，並列出記憶體範圍；這些是作者描述的情境，並非 REA 的跨平台保證。依目前客戶端、主機和樣本實測，並對照提供者文件調整請求逾時。

另一個限制是輸出太大。前述實測對少量 JavaScript 檔案就產生數十 MB 的 Evidence，文章建議儲存原始結果，讓 Agent 閱讀摘要視圖。大量反組譯或批次反編譯同樣會吃掉上下文；範圍越寬，Agent 越難核對每個推論。先縮小問題到函式、模組或行為，再保留可回查的原始位置。若分析標示 partial 或 unknown，它表示覆蓋不足，不能把未觀察到的路徑寫成不存在。

要特別區分「摘要省略了細節」與「分析本身沒有證據」。摘要視圖的目的，是讓 Agent 先看涵蓋情形與重點，再按需要回查完整 Evidence；它不會憑空補出未知的呼叫關係。若回答引用了摘要未展示的細節，就回到對應的原始紀錄查位置、提供者與限制。這也讓長任務能分段進行：先形成可驗證的窄問題，再擴到相鄰模組，而不是一次把所有反編譯文字交給模型。

推論、混淆與行為盲區

這是圖 13-1 的輸出缺口：工具提供的片段可能難以解讀，或根本未涵蓋決定行為的外部狀態。

反編譯器輸出的是可讀的重建結果，並非原始碼。ida-pro-mcp README提醒模型在混淆碼上容易失準，列出字串加密、匯入雜湊、控制流程展平與反編譯干擾技巧等障礙。這些問題不會因換成 REA 自動消失；REA 仍依賴底層引擎與 Agent 對片段的理解。對關鍵結論，要對照組語、字串、交叉參照與可重複的行為觀察。

靜態分析也看不到所有執行時事實：某些分支取決於伺服器回應、使用者帳號或當下環境。影片筆記 VID-328 以會員資格為例，指出本機客戶端可能只看得到請求，無法從客戶端直接知道伺服器如何裁決。這是影片說法，用來說明推論邊界；不能當成對任一特定服務的驗證結果。對外部狀態保留「未知」，比補上一個看似合理的流程可靠。

升級會更改結果與儲存資料格式

官方 6.1→6.2 遷移指南明說專案採用 always-bump-minor，次要版本增加也可能破壞相容性。該次升級將 Evidence 直接放在 structuredContent，移除了舊的 result 包裝；成功與錯誤結果形狀也不同。自製 MCP 消費端應先檢查 isError，再讀成功欄位。以下程式碼逐字照抄遷移指南的錯誤處理範例。

6.2：先辨識錯誤結果
if (reply.isError === true) {
  const text = reply.content.find((part) => part.type === "text");
  if (text === undefined) throw new Error("REA error has no text diagnostic");
  const { error: diagnostic } = JSON.parse(text.text);
  // Handle diagnostic.code, diagnostic.message and diagnostic.details.
}

同一份指南還說明：舊 Evidence 若缺少參與身分計算的 analysis_profile，不能只補欄位而沿用舊 ID；快照須有完整的工作流與提供者綁定；舊版 process capture 缺少事件日誌時不能被無損轉換。正確作法是保留舊檔作歷史紀錄，在新版重新觀察，並用新路徑寫入新快照。下列指令是指南原文示例。

6.2：用新路徑重建快照
rea analyze /absolute/path/to/program --provider ghidra --snapshot /absolute/path/to/analysis/program-6.2.json

重新分析還要記住時間差。新版工具可能修正了解析方式，但目標檔案、來源樹或執行環境也可能同時改變；新舊結果不同，不能立刻歸因於 REA 升級。遷移指南要求保留原始產物，理由就在這裡：舊資料記錄的是當時觀察，不應被改寫成新版格式後假裝具備當時沒記下的欄位。要做版本比較，先確認樣本身分與分析條件，再解讀差異。

⚠️
版本資訊以當前官方 README 為準

截至 2026-10-13，各來源對工具數、版本與 Node.js 要求說法不一。本章的 6.1→6.2 僅是官方遷移文件的具體案例，不能推定之後版本仍用相同欄位或路徑。升級前讀對應版本文件，保留原始產物與目標檔案，再核對重新分析的結果。
