第 10 章 · Part 4：實戰、評測與比較

實戰案例：DX-Ball、Notion 與 TH04

把工具回傳的線索，變成能重查與核對的行為說明

三個案例，三種證據

前幾章分別介紹原生程式、封裝應用與其他目標。現在換成真實問題：遊戲如何把位置變成音效左右定位？桌面應用的複製動作如何穿過程序邊界？舊式 DOS 遊戲如何排列瞄準玩家的彈幕？三個案例都以明確問題開始，但它們的證據型態與驗證強度不同。

閱讀案例時，把「REA 直接回傳的位址、指令或來源範圍」、「調查者連起來的解釋」、「另行執行的測試」分開。這樣才知道一個結論是檔案事實、合理推論，還是已在特定條件下測過的行為。

DX-Ball：從殘缺反編譯到聲音定位

官方案例對 Agent 的起始問題範圍小而明確，並要求解釋計算及展示程式碼。目標是使用者自己的 DX-Ball 1.07 執行檔；REA 本身不附遊戲。調查者先看 0x00406400 的偽程式碼，結果只顯示 __ftol() 附近的轉換，因此回頭讀實際 x86 指令與呼叫者。

原文：DX-Ball 提問
Use REA to find how DX-Ball calculates sound panning. Explain the calculation and show the code.
原文：音效定位函式的選取指令
0x406409: MOV EAX, dword ptr [EBP + 0x8]
0x40640c: MOV dword ptr [EBP + -0xc], EAX
0x40640f: FILD dword ptr [EBP + -0xc]
0x406415: FMUL double ptr [0x00420068]
0x40641e: FSUB double ptr [0x00420070]
0x406427: FMUL double ptr [0x004210a0]
0x406430: CALL 0x0041678c
0x40643e: RET

指令顯示整數輸入進入浮點運算，依序乘上資料區的值、減去另一個值，再乘上縮放量。沿呼叫者可知輸入是磚塊橫向螢幕座標；讀取資料位元組得出 1.5625、500.0 及初始縮放值 1.0。案例據此寫出下列 C 函式。這是依證據重建的可讀程式，不能僅憑偽程式碼把它稱為原始碼。

原文：重建的 C 函式
DxBallInt dxball_screen_pan(DxBallInt x)
{
    double pan;
    pan = (double)x;
    pan = pan * 1.5625;
    pan = pan - 500.0;
    pan = pan * dxball_pan_scale;
    return (DxBallInt)pan;
}

案例另做兩種核對：逐一比對螢幕位置 0 到 640 的每個整數值，並搭配五種縮放量（0、0.5、1、20、−1），共 3,205 組原始 x86 與重建函式的回傳值；以固定的 Visual C++ 4.0 工具鏈編譯，套用經審核的重定位並核對參照常數後，完整函式的 63 個位元組吻合。這些數字是該案例於指定檢查點的記錄，並非 REA 對所有程式的保證。案例原文與重建專案保留調查與驗證脈絡。

Notion：沿剪貼簿訊息跨越程序

Notion 案例從 Electron tab preload 讀起。REA 對保存的 preload.js 做靜態分析，定位公開給頁面的 __electronApi 以及 invoke 操作，並附原始壓縮檔的行與欄範圍。這些位置是工具直接提供的起點；調查者再打開相應片段，找出 clipboard 成員和 notion:clipboard:write 通道。

原文：REA 回傳的 preload 位置
api_key: "__electronApi"
api_status: "dynamic"
source: preload.js:1:22764–22828

operation: "invoke"
channel_expression: "e"
source: preload.js:1:6486–6522

接下來要跨兩個 wrapper：頁面呼叫透過 preload 的 ipcRenderer.invoke 送往 main process；main process 以 ipcMain.handle 登記接收者，確認 sender 後呼叫 Electron 的 clipboard.write。下方是案例作者從封裝 JavaScript 簡化並重新命名變數的片段，目的是呈現路徑，不能當成原始壓縮碼逐字引用。

原文案例：簡化後的接收端
handleRequestFromRenderer.addListener(
  "notion:clipboard:write",
  (event, data) =>
    isNotionWebContents(event.sender)
      ? clipboard.write(data)
      : undefined
);

案例還描述網頁編輯器把文字與 HTML 放進剪貼簿，並用 HTML 中的 ID 對應本機保存的結構化區塊資料。這一段來自另一期快取的 web assets 與抽出模組的測試；它與桌面 preload 的 REA 定位不是同一次桌面 UI 實測。把兩組來源分清楚，才能避免把「模組測試可還原區塊」誤寫成「所有桌面複製都已被動態觀察」。詳見Notion 案例。

TH04：從 16 位元指令到瞄準彈環

TH04 案例研究 PC-98 DOS 遊戲的彈環。範例提問要求找出彈環如何生成、如何瞄準玩家。調查先驗證 MAIN.EXE 的 DOS 載入映像，再閱讀 bullet_velocity_and_angle_set() 的指令、偽程式碼與參照；這讓載入位址與檔案位元組的關係有明確依據。

原文：TH04 提問
Use REA to find how TH04 creates a ring of bullets and aims it at the player. Explain the calculation and show the code.
原文：彈環分角指令
0x2d0eb: MOV AX, SI
0x2d0ed: SHL AX, 0x8
0x2d0f0: MOV DL, byte ptr [0x53af]
0x2d0f9: IDIV BX

案例指出遊戲把一整圈表示為 256 個角度單位。索引左移八位後除以彈數，得到相鄰彈的角度；若是瞄準環，再加上由玩家與發射原點座標差算出的方向，最後加樣板旋轉量。十六顆彈時，基礎間距是 16 個單位。下列可讀 C++ 是案例對瞄準環分支的摘要；完整重建程式也處理散射、堆疊與隨機彈型。

原文：瞄準彈環摘要
unsigned char aimed_ring_angle(
    int index, int count,
    int player_direction,
    unsigned char rotation)
{
    int angle = index;
    angle = (angle * 256) / count;
    angle += player_direction;
    angle += rotation;
    return (unsigned char)angle;
}

重建專案以固定的 Turbo C++ 4.0J 工具鏈核對整段彈幕產生碼，案例記錄 2,139 個位元組吻合，兩次乾淨建置產生同樣結果。這涵蓋該段程式與其依賴的編譯條件，尚不能推成整款遊戲的畫面、輸入或時序都已相同。來源也明言原始目標的獨立 pristine dump 來源仍有待補足。詳見TH04 案例。

把案例化成自己的調查節奏

三份案例共同的實務順序是：鎖定一個功能與檔案，從 REA 的定位結果向外追，記下每個推論跨過的缺口，再用可獨立執行的測試驗證重要結論。DX-Ball 與 TH04 都把重建程式與原始執行檔比對：前者核對函式輸出與編譯位元組，後者核對彈幕程式段的編譯位元組；Notion 展示的是跨封裝檔與程序邊界的靜態鏈路，另有範圍較窄的模組測試。驗證方法要隨問題選擇，不能只因為 Agent 能寫出一段程式，就宣稱整個產品已重建。

如果要模仿這個流程，可先把問題縮到單一輸入與單一輸出，例如「這個位置如何變成聲道值」，再要求 Agent 列出每個中間步驟的來源。對封裝應用，來源應含檔案與原始位置；對二進位檔，應含函式、指令或資料位址。最後另設測試，讓寫出的程式在明確輸入下與權威目標比較。測試通過只涵蓋所列輸入與環境；未測的路徑仍要留在未知清單。

⚠️
數字與版本只屬於來源檢查點

案例的測試數、相符位元組與軟體版本均來自各案例記錄，不代表截至 2026-10-13 的專案即時進度。其他素材對 REA 工具數與版本說法不一；現行能力以 官方 README 與實際安裝結果為準。
