第 8 章 · Part 3：分析目標

原生二進位檔與函式檔案

讓函式、指令與資料共同支撐一項行為判斷

從檔案進入函式

前章的 JavaScript 可以沿模組與呼叫路徑閱讀；原生程式則要先由分析引擎辨認機器指令、函式邊界與參照。REA 提供 CLI 與 MCP 兩種入口，由 Hopper、Ghidra 或 IDA 回傳偽程式碼、組合語言、字串、符號及呼叫關係。這些是分析結果，不等於原始碼。函式庫也可作為目標，但匯出符號只是起點，不能從名稱推斷全部行為。

以 Ghidra 為例，官方原生調查文件先檢查檔案，再搜尋可能的函式。第二行的 entry 是搜尋詞，不保證每個程式都有同名函式。應從結果選一個確切名稱或位址，再要求函式資料（function dossier）、指令或反編譯結果。

原文：原生調查起手式
rea inspect /absolute/path/to/program --provider ghidra --json
rea search /absolute/path/to/program entry --kind procedures --provider ghidra --json

若已知道要看的函式，REA 的原生分析示例直接以 main 為選擇器；換成自己的檔案時，仍須用實際盤點得到的名稱或位址。一次性 CLI 命令可用 npx rea-agents@latest 前綴；全域安裝後則可直接使用 rea 命令。CLI 呼叫會匯入、分析並關閉會話；Agent 的 MCP 查詢則可在開啟的會話中重用已匯入的目標。

原文：查詢已知函式
npx -y rea-agents@latest function /absolute/path/to/program main \
  --provider ghidra --json

讀結果時，先看函式入口、指令範圍與呼叫關係是否彼此一致，再追問那個函式為何與研究中的功能有關。搜尋到一個看似相關的字串，不代表顯示字串的程式就是核心邏輯；它可能只是錯誤訊息、介面標籤或測試資料。從字串往交叉參照走，再核對實際讀取該位址的指令，才能縮小範圍。若符號已被去除，應保留位址和檔案身分，避免把 Agent 自行取的暱稱當成原程式的函式名稱。

別讓偽程式碼替證據作決定

REA 官方 DX-Ball 案例說明了聲音左右定位。位址 0x00406400 的第一份偽程式碼主要只看見 __ftol()，似乎沒有算式。再看指令，整數從堆疊讀入，經 FILD 轉進浮點運算。接著沿呼叫者往回讀，才能知道傳入的不是任意整數，而是磚塊的螢幕橫向位置。

原文：函式內的輸入
MOV EAX, dword ptr [EBP + 0x8]
MOV dword ptr [EBP + -0xc], EAX
FILD dword ptr [EBP + -0xc]
原文：呼叫者片段
ADD EAX, 0x14
PUSH EAX
CALL 0x00406400

同一案例的資料位元組解碼出 1.5625、500.0 與縮放係數 1.0。指令次序與呼叫者一起支持 pan = (x × 1.5625 − 500.0) × scale。這裡的算式是針對該份 DX-Ball 執行檔的重建結論，不是所有遊戲的音效公式；完整的驗證留到第十章。

這個例子也顯示「先反編譯，再用偽程式碼作答」的缺口：反編譯器在轉換呼叫附近漏掉了輸入與前面的運算，卻沒有表示整個函式完全無法分析。組合語言中的堆疊讀取指出參數位置；呼叫者告訴我們參數的業務意義；資料區給出實際常數。三條線索互相約束後，公式才有可檢查的來源。若其中一條線索缺席，答案要縮小，例如只說「此處讀取了一個整數」，暫不把它命名為螢幕座標。

ℹ️
證據層級

反組譯可顯示實際指令；偽程式碼是工具的重述；呼叫者與資料參照補足輸入含義。靜態呼叫邊不能單獨證明執行時一定走到該路徑。

追查時保留選擇器與未知

調查從一個精確的函式識別開始，逐步讀取指令、呼叫目標、交叉參照與資料型別。Ghidra 的 resolve-native-call-targets 會區分直接、已解析的間接、模糊及未解析等結果；未解析不應被 Agent 補成確定目標。型別資訊來自分析資料庫，若原始檔去除符號或缺少偵錯資訊，資料庫中的結構也未必能還原原始宣告。

相同函式名稱可能有多個候選；從工具回傳的名稱清單選擇，必要時改用位址。內部位址與函式入口也要分開記錄。修改來源檔、換分析引擎或換分析設定後，舊快照不能自動當作新檔案的證據。回報時記下檔案身分、provider（提供者）、確切選擇器與尚未確認的關係。

要重建可維護的程式時，可把調查分成小問題：參數從哪裡來、哪些常數影響輸出、回傳值由誰使用。每找到一個答案，就保存對應指令或資料位置，再寫一小段可驗證的程式。這能避免把大量互不相關的偽程式碼一口氣轉成看似完整的實作。若準備對照兩個版本，也應先確認兩份檔案的身分與各自的函式選擇器，不能假設相同位址仍代表相同功能。

Go 與 WASM 走不同入口

若問題只問 Go 執行檔的內嵌編譯器字串、模組、替換依賴或建置設定，可先用內建讀取器。它讀本機 ELF、PE 或單一架構 Mach-O 的建置資訊，不執行檔案，也不需 Go 或反組譯引擎。沒有辨認到 build_info，只代表這次未找到受支援的記錄，不能斷言它不是 Go 程式。內嵌版本與依賴文字也不是供應鏈真實性的證明。

原文：Go 建置資訊
rea inspect-go-binary /absolute/path/to/application --json

WASM 有自己的離線檢查：使用者提供 WABT，REA 驗證所選模組並回傳區段、匯入匯出形式與 WAT；REA 不代裝工具、不抓取產物，也不執行 WASM。open_binary 不是此路徑；WAT 是解碼表示，不是原始碼，也無法證明執行時如何載入。若另外提供 JavaScript glue，字面上的檔名只構成候選關聯，動態組出的路徑仍待追查。

原文：WASM 離線檢查
REA_WABT_BIN_DIRECTORY=/absolute/wabt/bin rea inspect-wasm-artifact \
  /artifacts/module.wasm --glue_paths /artifacts/glue.js \
  --candidate_paths /artifacts/other/module.wasm --format json
