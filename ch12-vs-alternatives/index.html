第 12 章 · Part 4：實戰、評測與比較

與 GhidraMCP、ida-pro-mcp 的比較

先問要分析什麼，再問 Agent 應該接哪一種工具。

比較的基準：橋接範圍與調查產物

REA、LaurieWired 的 GhidraMCP，以及 mrexodia 的 ida-pro-mcp 都能讓支援 MCP 的 Agent 呼叫逆向工具。差異首先在工作範圍。REA 把多類目標與分析提供者放進同一套 CLI／MCP 流程；另兩者各自圍繞 Ghidra 或 IDA 的資料庫與操作介面。這是產品定位的差異，並不能直接推論哪個反編譯結果較準。REA 專案、GhidraMCP 專案及ida-pro-mcp 專案都有各自的實作與前置條件。

若目標從 Electron 的 JavaScript、IPC 橋接延伸到原生模組，REA 的統一調查流程較貼合任務；若研究者已經在 Ghidra 或 IDA 中整理函式、註解與型別，直接接該工具的 MCP 橋接，便能沿用熟悉的資料庫。這個判斷來自三個專案文件所列的功能範圍，不代表同一個樣本的實測效能排名。

REA：跨目標調查與可追溯證據

REA 的分析對象包括原生二進位檔、JavaScript／Electron、.NET、APK 與網站觀察等；需要反編譯原生檔案時，它仍須連接 Hopper、Ghidra 或 IDA。它交給 Agent 的不只是一段反編譯文字，還有包含目標身分（subject）、提供者、操作、來源位置、信心與限制的 Evidence 紀錄。快照與匯出流程讓研究者能回看同一批觀察。前章已討論如何評測 Agent，本章只比較工具交付給 Agent 的材料。

這種包裝對「一個問題要穿越多種檔案」尤其重要。以桌面程式的功能調查為例，研究者可能先在 JavaScript 找到事件名稱，再追到原生模組的函式，最後比較執行時現象。REA 將這些觀察放在同一種證據結構中，較容易指出哪一步是直接觀察、哪一步仍是推論。不過證據欄位完整不代表推論自動正確：來源位置可能只支持「找到呼叫關係」，未必支持「已證明業務用途」。讀者仍須對照原始片段與限制欄。

以下指令逐字取自 REA 實測文章，展示明確選取 Ghidra 提供者的 CLI 路徑；它不是「只裝 REA 就有 Ghidra」的意思。

REA：指定原生分析提供者
rea analyze /absolute/path/to/program --provider ghidra --json

REA 適合要在多種檔案及行為觀察間建立證據鏈的任務，但統一介面也帶來較多輸出與設定。若只需要對一個已開啟的二進位檔查 xref 或重新命名函式，專用橋接可能更直接。

GhidraMCP：沿著 Ghidra 的資料庫工作

LaurieWired/GhidraMCP 的路徑是 MCP server 對接 Ghidra 擴充套件，將 Ghidra 的功能提供給 Agent。它也支援透過 PyGhidra 匯入與分析二進位檔的無介面（headless）模式，因此「一定要開 Ghidra GUI」並不正確。無介面模式仍要安裝相容的 Ghidra、擴充套件並設定環境。其 README 提供下列 Claude Code 註冊指令；使用前須先完成擴充套件安裝與啟用。

GhidraMCP：README 的 Claude Code 註冊例
claude mcp add ghidra -- uvx --from git+https://github.com/LaurieWired/GhidraMCP ghidra-mcp --ghidra-server http://127.0.0.1:8080/

對已熟悉 Ghidra 專案、想讓 Agent 查詢反編譯結果及修改分析註記的人，這條路線的概念負擔較小。不過「橋接 Ghidra」與「REA 用 Ghidra 作提供者」是兩種整合方式：前者直接暴露 Ghidra 工作環境，後者把分析納入 REA 的 Evidence 與跨目標工作流。兩者是否有同名操作，仍須看當時各自文件。

安裝步驟也反映此差別。GhidraMCP README 的 GUI 路線要先安裝擴充套件、重新啟動 Ghidra，再到 File → Configure → Developer 確認 GhidraMCPPlugin 外掛啟用，讓 MCP server 指向該 Ghidra 實例；無介面路線另有 PyGhidra、環境變數與擴充套件要求。REA 的 CLI 指令則先選定提供者，由 REA 組織查詢與輸出。兩條路線都會受 Ghidra 安裝及分析品質影響，不能因其中一條註冊命令較短，就推定整體部署一定較簡單。

ida-pro-mcp：IDA 與 idalib 的細緻操作

mrexodia/ida-pro-mcp 聚焦 IDA。其 README 列出反編譯、反組譯、交叉參照、函式與型別修改、搜尋及可選的除錯器工具；新版文件也描述 idalib 的無介面（headless）supervisor 與多資料庫會話（session）。這並非只能操作目前 GUI 游標的薄封裝。下列啟動指令逐字取自該 README；它要求已安裝並啟用符合條件的 IDA Pro 與 idalib，README 明言 IDA Free 不受支援。

ida-pro-mcp：stdio 無介面服務
uv run idalib-mcp --stdio

多資料庫會話對同時追查主程式與函式庫有用：Agent 每次呼叫工具都須帶上明確的 database 參數，而不能假定有隱含的「目前資料庫」。README 也列出註解、重新命名、修正型別及補丁等可改變資料庫的操作；使用時要分清唯讀查詢與寫入動作，並保留人工審查。這項能力適合已用 IDA 維護分析成果的團隊。若調查還要包含 Electron 邊界或網站觀察，則需另行組織那些資料，或評估 REA 的跨目標流程。

ℹ️
IDA 官方方案也存在

mrexodia 專案 README 開頭明確建議改用 Hex-Rays 的官方 IDA MCP Server。本章比較的是題目指定的 mrexodia/ida-pro-mcp；若已採用 IDA，部署前也應查看官方方案的當前文件。

比較時還要問「結果要交給誰」。若 Agent 的回答須讓另一位工程師獨立追查，應保留目標檔案身分、反編譯位置、查詢條件及未知處；REA 的 Evidence 正是為此設計。若分析者主要在 Ghidra 或 IDA 專案內協作，函式名稱、註解與型別修改本身可能更符合日常交接方式。兩種產物各有用途，仍要看接收者能否取得相同樣本、相容的工具與必要的授權。

⚠️
版本與數字容易過期

截至 2026-10-13，各來源對 REA 的 MCP 工具數與 Node.js 要求記載不一：實測文章引述安裝指南的 133 個工具，另一篇介紹文章則寫 126 個。GhidraMCP 與 ida-pro-mcp 的安裝方式也在演進。本章不以工具數排名，部署時以各專案當前 README 為準。
